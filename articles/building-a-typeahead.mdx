Most typeaheads are almost good. Then they flicker, or feel laggy, or spam the screen reader, or let an old request overwrite the newest result. None of these problems are hard to fix — they’re small defaults that need to work together. Here’s the version I’d actually ship.

Try `iphone`, `laptop`, or `gaming`. Type fast and watch the debounce. Type the same query twice and watch the cache hit. Type nonsense and you’ll see the empty state. The API usually responds in 50–250ms, with an occasional slower 500–800ms request.

## The four numbers

A good typeahead is mostly about managing the waiting window.

| Number | Value | Why |
|---|---:|---|
| Minimum query length | 2 | One character is usually too broad to be useful |
| Debounce | 250ms | Groups quick keystrokes without making search feel slow |
| Loading UI delay | 150ms | Avoids flashing a skeleton for fast responses |
| Cache TTL | 60s | Keeps repeat searches instant without holding stale data for long |

Lower the debounce too far and you send noisy requests; push it past 300ms and fast typers start to feel the delay. The skeleton delay matters just as much: a 250ms debounce plus a 50ms fetch is fine without loading UI, but a 250ms debounce plus an 800ms fetch needs a skeleton.

## The cache

Use a module-level `Map`, keyed by normalised query, with TTL and LRU eviction. It survives component remounts — useful when the popup opens and closes — but resets on page reload.

<CodeBlock name="cache.ts" lang="ts">
{`type CacheEntry = { results: SearchResult[]; expiresAt: number };
const searchCache = new Map<string, CacheEntry>();

function readCache(q: string) {
  const k = q.trim().toLowerCase();
  const entry = searchCache.get(k);
  if (!entry) return undefined;

  if (entry.expiresAt <= Date.now()) {
    searchCache.delete(k);
    return undefined;
  }

  // Touch the entry so it moves to the back of the Map.
  searchCache.delete(k);
  searchCache.set(k, entry);

  return entry.results;
}`}
</CodeBlock>

The useful trick is reading the cache synchronously against the live query, not just the debounced query. If the answer is already in memory, the user shouldn’t wait for the debounce.

<CodeBlock name="typeahead-demo.tsx" lang="tsx">
{`const cached = useMemo(() => {
  if (trimmed.length < MIN_QUERY_LENGTH) return undefined;
  return readCache(trimmed);
}, [trimmed]);

const effective = cached ?? results;`}
</CodeBlock>

That’s what makes re-typing a previous query feel instant.

## Abort old requests

When the user keeps typing, the previous request is stale. Without cancellation, a slow old response can land after a newer one and overwrite the correct result.

<CodeBlock name="use-product-search.ts" lang="ts">
{`useEffect(() => {
  const controller = new AbortController();

  setStatus("loading");

  mockSearch(query, controller.signal)
    .then((data) => {
      if (controller.signal.aborted) return;

      writeCache(query, data.results);
      setResults(data.results);
      setStatus("success");
    })
    .catch((err) => {
      if (controller.signal.aborted) return;
      if (err instanceof Error && err.name === "AbortError") return;

      setStatus("error");
    });

  return () => controller.abort();
}, [query]);`}
</CodeBlock>

There are two checks here. The `.then()` guard handles the case where the request resolves just as the effect cleans up, and the `.catch()` guard treats cancellation as expected behaviour, not a real error.

## Delay the skeleton

Showing a skeleton for every fast response makes the UI feel worse: it creates a flash with no useful information. So delay it.

<CodeBlock name="use-delayed-flag.ts" lang="ts">
{`/**
 * Returns true only after \`active\` has stayed true for \`delayMs\`.
 * Useful for avoiding skeleton flashes on fast responses.
 */
function useDelayedFlag(active: boolean, delayMs: number) {
  const [delayed, setDelayed] = useState(false);

  useEffect(() => {
    if (!active) {
      setDelayed(false);
      return;
    }

    const id = window.setTimeout(() => setDelayed(true), delayMs);
    return () => window.clearTimeout(id);
  }, [active, delayMs]);

  return delayed;
}`}
</CodeBlock>

This pattern is useful everywhere. Wait 100–150ms before showing loading UI and most fast responses never need it.

## Virtualise, but keep it small

A 500-item list with 64px rows means 32,000px of rendered content. Most browsers can handle that, but lower-end devices may still jank while scrolling. For a fixed-height typeahead list, a small virtual list is enough.

<CodeBlock name="virtual-list.ts" lang="ts">
{`function useSimpleVirtualList({ itemCount, itemHeight, containerHeight, overscan = 5 }) {
  const [scrollTop, setScrollTop] = useState(0);
  const rafRef = useRef<number | null>(null);

  const startIndex = Math.max(0, Math.floor(scrollTop / itemHeight) - overscan);
  const visibleCount = Math.ceil(containerHeight / itemHeight);
  const endIndex = Math.min(itemCount - 1, startIndex + visibleCount + overscan * 2);

  function onScroll(e) {
    if (rafRef.current !== null) return;

    rafRef.current = requestAnimationFrame(() => {
      rafRef.current = null;
      setScrollTop(e.target.scrollTop);
    });
  }

  // ...
}`}
</CodeBlock>

The important part is the `requestAnimationFrame`. Scroll events can fire faster than React can render, so coalescing updates to one per frame keeps the rendered window closer to the scrollbar position.

For a serious production list, I’d use `@tanstack/react-virtual`. For a fixed-height typeahead, a tiny hook is usually enough.

## Accessibility: announce once

Screen readers should hear the final result, not every intermediate state. Use one visually-hidden live region: keep it empty while typing or loading, and populate it when the result has settled.

<CodeBlock name="typeahead-demo.tsx" lang="tsx">
{`let liveAnnouncement = "";

if (showPopup && !isSearching) {
  if (showError) {
    liveAnnouncement = error ?? "Search failed.";
  } else if (items.length === 0) {
    liveAnnouncement = \`No results for "\${trimmed}".\`;
  } else {
    liveAnnouncement = \`\${items.length} \${items.length === 1 ? "result" : "results"}.\`;
  }
}

return (
  // ...
  <div role="status" aria-live="polite" className="sr-only">
    {liveAnnouncement}
  </div>
);`}
</CodeBlock>

`role="status"` with `aria-live="polite"` lets the screen reader announce results without interrupting the user. The key is restraint: don’t announce loading on every keystroke.

## What I’d defend in an interview

- **250ms debounce** because it reduces noisy requests without making search feel slow.
- **150ms skeleton delay** because fast responses don’t need loading UI.
- **Module-level cache with TTL** because remounting the component shouldn’t lose useful results.
- **Live-query cache reads** because cached answers should feel instant.
- **AbortController hygiene** because stale requests should never win.
- **One settled live-region announcement** because accessibility should be calm, not noisy.

The code is small. The hard part is knowing which tiny decisions make the whole interaction feel fast, stable, and respectful.
